# 为已选餐单选择买法

核价阶段使用。比较的目标是用户愿意吃的这一顿，先固定主要食物，再找适用的购买组合；允许实质有益的调整，但保留原方案作比较。

## 建立可比条件

- 沿用已确定的门店、取餐方式、时间和人数，按 `query-meals` 获取当次可售商品编码。缺这些条件时，说明价格待核；不要用活动起售价补上。
- 用 `query-meal-detail` 核对套餐实际子项、大小份、饮料规格与特调限制。单点与套餐比较时，对齐食物及数量；拆成多单会产生不同费用或优惠条件，不能按一单结果推断。
- 使用用户已说明或工具可靠核实的麦金卡身份与当前权益。没有专门的会员身份工具时，不从积分余额、券名称或历史订单推断当前持卡情况，也不伪造跨身份试算。
- 只有当前门店、渠道和时间允许的购买方式才是可行候选。不能用到店优惠回答「今晚必须外送」的实付价。

## 分清优惠的状态

| 证据 | 能得出的结论 |
| --- | --- |
| `campaign-calendar` 的活动价格 | 有这条活动线索，仍要核实资格、门店和组成 |
| `available-coupons` 中的券 | 按各条状态区分：如 `HAVING_RECEIVE` / 已领取可视作持有线索；未领取条目才是领取候选。两者都还需核实当前订单适用性 |
| `query-my-coupons` 中的券 | 用户持有这张券，尚不能保证用于当前门店和订单 |
| `query-store-coupons` 中的券及规则 | 当前门店/渠道下的适用线索，还需核对商品、数量、时间、使用次数等条件 |
| `calculate-price` 对完整方案的成功结果 | 当前所传方案与优惠参数的试算结果；仍需识别返回的费用范围和优惠是否真正生效 |

候选券的 `couponId`、`couponCode` 和商品编码来自实际响应，按当前 schema 填写。没有字段或未返回的规则就不补猜。可领取的券作为条件备选展示；领取后要重新核实，不能声称已领到。用户说「帮我省钱」并不自动授权开卡、领券、积分兑换或创建订单。

## 比较购买组合

围绕当前餐单选择相关候选，例如分别单点、同组成套餐、已核实的会员组合、适用券组合，以及必要的「套餐＋单点补齐」。不需要穷举无关商品或全部券排列。

- 对每个候选传入完整商品、数量、所选套餐子项、特调和相应券，调用 `calculate-price`。商品级券依接口规则关联对应项目；不要将一张券重复挂到多个项目。
- 麦金卡权益与优惠券不能凭直觉相加。只有规则允许且试算确认生效，才报叠加后的价格；不可叠加时比较各自可行的买法。
- 核对试算有没有改变组成、遗漏商品、拒绝优惠或只返回部分金额。接口不支持的组合标为未核实，不在本地编造一个可支付价。失败时不创建订单来探测价格，也不反复提交同样的无效参数。
- 相同组成的方案共享相同营养总量，蛋价比分母使用各自的可核实实付金额。组成变化的方案重算营养，并说明变化，不把它称作「同一顿便宜了」。
- 比较费用范围一致的总支出；配送、包装、购卡、付费券成本按本次实际需要计入。结算已包含的优惠或费用不再加减，不能用赠品标价、节省百分比或未来返券抵扣本次现金支出。
- 报「省 X 元」要说明基准。同组成单点 23 元、套餐 21 元，才是同样食物省 2 元。换小份或少买后便宜，应同时说明少了什么。

## 将变化交回给用户决定

优惠可提示一次有意义的小调整，例如「这份搭配已经核价；另一张券需要换小食，能少花 X 元，营养变化是……」。用户明确指定要中薯，就保留中薯主方案；换小薯的优惠是备选，不默认接受。

餐品、份量、特调、门店、渠道、时间、卡券资格任一改变，先前受影响的报价需要重算；营养只重算变化的食物。用户否决某个调整后，不在下一轮又因优惠推荐回来。

结果用自然语言说明选择理由和实付条件。未核价时可先给搭配，提出完成报价所缺的关键条件；不要把未完成的查询写成「查下来最便宜」。
